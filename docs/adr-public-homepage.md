# Public homepage integration decision (2026-10-10)

The Flutter web bundle remains rooted at `/`. Its `index.html`, bootstrap, CanvasKit files, manifest, legal pages, and deep-link fallback are one release unit. The new homepage is a separate static build in `website/`, mounted read-only at `/var/www/landing`. Nginx exact locations serve `/` (Russian default), `/en/`, `/uz/`, `robots.txt`, and `sitemap.xml` from that mount; a dedicated `/landing-assets/` alias serves its assets. All other application paths continue through the existing Flutter root and fallback. The marketing build cannot overwrite or shadow Flutter files. The only Flutter source change is the manifest launch URL `/feed` so an installed app does not open the new homepage.

The site uses a Python standard-library static generator and source CSS/JS/SVG. This avoids a production Node runtime, client rendering, third-party assets, and new CSP origins. Generated asset filenames include content hashes. HTML is not cached; assets may be cached immutably. Language pages are separate crawlable documents. Existing public legal paths remain Flutter-bundle files, and Terms links to the existing Flutter legal route.

Integration uses the existing versioned release procedure: build and validate Flutter and website outputs independently, copy both into one new release directory, then switch the Compose stack only after review. No database change is involved. The currently mounted artifact must not be edited in place.
